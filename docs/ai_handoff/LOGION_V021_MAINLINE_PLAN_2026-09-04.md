## 0. 版本目标

修复 RC8 审计发现的阻断/严重问题，确保"人工可投入使用"，并让线上版本可核验。
不做任何功能演进；演进内容见 `LOGION_FEATURE_EVOLUTION_PLAN_2026-09-04.md`，与本版本严格隔离。

### 1.3 非代码前置事项：暴露部署 build SHA（T-00）

**现状（本轮核实）**：

- 后端 `/health/live`、`/health/ready` 已返回 `version` 字段，来源 `settings.version`，读环境变量 `LOGION_VERSION`（`config.py:17,22`，`env_prefix="LOGION_"`）。
- 生产部署手册 `infra/runbooks/aliyun-production-release.md:536` 执行 `set_env_value LOGION_VERSION "${SOURCE_SHA}"`；`compose.yaml:66/134/262` 把该变量传给 api/worker/backup。
- **但**：nginx 只把 `/api/` 转给 API（`infra/nginx/nginx.conf:38`），后端健康路由没有 `/api` 前缀，所以公网 `/health` 命中的是**前端**路由 `apps/web/src/app/health/route.ts:7`，其 `version` 写死 `"0.1.0"`。2026-09-05 实测 `https://logion.work/health` 返回 `{"status":"ok","service":"web","version":"0.1.0"}`。
- `compose.yaml` 的 web 服务**没有**传 `LOGION_VERSION`。

**结论**：GPT 说"健康接口不暴露 build SHA"对公网成立；后端容器内很可能已经有答案。

**行动（分两步，第一步纯运维）**：

1. **运维（0.5 h，无代码）**：在生产主机执行手册 `:645` 的命令读取 API 容器内 `/health/ready`，记录 `version` 值；同时 `docker inspect` 四个容器镜像 digest，与 RC7/RC8 候选 manifest 对照。**这一步就能回答"线上是哪版"**，并应把结果写回 `docs/development/V020_STATUS.md`。
2. **代码（1 h）**：`apps/web/src/app/health/route.ts` 改读 `process.env.LOGION_VERSION ?? "unknown"`；`compose.yaml` web 服务加 `LOGION_VERSION: ${LOGION_VERSION:-0.1.0}`。可选：nginx 增加 `location = /api/health/ready` 反代到后端，或前端 `<meta name="logion-build">`。
   注意 web 镜像是 `standalone` 运行时（`apps/web/Dockerfile:27-40`），环境变量在运行时读取，无需重建镜像即可通过 compose 注入。

## 3. 验收标准

- [ ] T-01、T-02（步骤 1/2）、T-03、T-04 全部合并，且**真实浏览器**验收通过。
- [ ] **失败路径**同样有正确反馈，全站不存在与事实相反的成功文案（T-01 组件测试断言 + T-03 逐模块失败路径实测）。
- [ ] `pnpm ci:fast` 全绿；`pnpm test:browser` 相关 spec 通过（现有 25 个 spec 文件，RC8 Nightly 基线 178 passed / 12 skipped）。
- [ ] `https://logion.work/health` 返回的 `version` 与部署的源码 SHA 一致；回归报告以该 SHA 为归因对象。
- [ ] 受限项如实标注"未验证"，**不得**以仿真结果冒充真机验收（T-04 需 VoiceOver 或 TalkBack）。
- [ ] GPT5.6 重新执行 58 项清单，**满足以下三条**：
  1. 27 项原通过项零回归；
  2. 与 T-01~T-04 直接对应的清单项（5.4、2.4、2.5、3.x、6.x、13.1）按"预期结果"判定通过或按新语义判定通过（见 §4）；
  3. 无新增 P0/P1。
- [ ] 无新增 P0/P1 问题。

**关于任务书中的"通过率 > 90%"**：本轮规划认为该指标**在 v0.2.1 范围内算术上不可达**，理由：58 项中 10 项受外部条件限制（邮箱、第二设备、真机、Lighthouse、导入）在 v0.2.1 不会解锁；9 项失败中 3.4/4.4/5.5（删除）与 4.3（依赖）、5.3（Note 链接）属 P2/演进范围；5.4（附件上传）即使文案修正，只要 ingest 开关关闭，"附件显示"仍不会通过。只修 P0/P1 后的严格通过上限约为 30-32/58（52-55%）。因此本计划把 90% 改为上面三条定向标准，并把此改动列入所有者决策（见 §6）。若所有者坚持 90%，则需要同时纳入 T-05/T-06、解锁 10 项受限条件、并开启附件 ingest，那已经不是 v0.2.1 的范围。
