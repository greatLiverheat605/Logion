# ADR-0030：Workbench v1 领域投影、持久化与权限边界

- 状态：Proposed
- 日期：2026-08-17
- 范围：下一产品版本的 Workbench v1 设计基线
- 产品基线：产品 Owner 已批准“统一 Today + 四个固定工作台 + 受控自定义工作台”
- 相关决策：[ADR-0004](0004-workspace-space-permission-model.md)、[ADR-0029](0029-adaptive-knowledge-space.md)

## 背景

当前 `PersonaDefinition` 只保存名称、图标、说明和路由列表，但产品已经分别围绕考试、学习、研究与导师场景聚合不同的领域对象、指标和下一行动。继续把它称为“画像”会混淆用户偏好、权限角色、数据范围和工作方式，也无法承载受控自定义、对象引用、布局恢复和多设备冲突。

本 ADR 冻结 Workbench v1 的架构边界，不批准迁移、OpenAPI、正式前端施工或生产能力启用。完整产品定义见 [`WORKBENCH_V1_PRODUCT_SPEC.md`](../product/WORKBENCH_V1_PRODUCT_SPEC.md)。

## 决策

### 1. Workbench 是投影，不是权限或数据容器

- 用户可见主术语使用“工作台”；“画像”仅作为旧设置和迁移期间的兼容语言。
- 工作台决定默认对象范围、模块、布局、视图、筛选和快捷操作，不决定 Workspace Role、Space 可见性或写权限。
- 服务端对每次对象读取、引用、移动和修改重新执行 Workspace/Space 授权。前端隐藏入口不构成权限控制。
- 真正的数据隔离继续由 Private/Shared Space 提供。切换工作台不切换身份、不扩大数据范围、不复制正式对象。

### 2. 固定工作台是代码维护的不可删除模板

系统提供学习、研究、考试和导师四个固定工作台。每类只有一个系统入口，具体课题、考试和项目由工作台内部领域对象承载，不通过创建多个同类固定工作台扩张导航。

- 固定模板的必需模块、对象语义和流程由产品版本控制；
- 用户可以隐藏入口、调整允许的模块顺序/密度、设置默认 Knowledge Base、默认视图和筛选；
- 用户不能删除固定模板、移除必要入口、改写领域对象定义或覆盖安全状态；
- 模板升级必须有版本迁移和兼容测试，失败时回退到对应系统默认值。

### 3. 自定义工作台使用受控式配置

自定义工作台可以从固定模板复制或从空白模板创建，允许：名称、图标、说明、受控辅助色、已注册模块、有限布局、默认 Knowledge Base、Saved View、筛选、快捷创建和有限属性。

禁止：

- 自定义 JavaScript、CSS、HTML、SQL、任意查询或自动化脚本；
- 新建任意服务端对象类型、权限、同步或 AI 正式写入规则；
- 把配置内容当作授权事实源；
- 使用原型污染键、未知 Schema 版本、重复 ID、无界递归或无界文本；
- 在 Attachment、Provider、Local Worker 或共享写入关闭时展示伪可用操作。

配置必须采用版本化 Schema、严格 allowlist、总大小/字段/枚举/层级限制、乐观版本和 409 冲突处理。配置失效时回退到基础学习模板，并保留可修复或导出的原配置副本。

### 4. 当前 PersonaSetting 只作为迁移来源

- 现有 `PersonaSetting` 不直接扩展为任意 `workbench-v1` JSON。
- `activePersonaId`、自定义名称/图标/说明和路由偏好可一次性转换为 Workbench v1 偏好或自定义草稿。
- 迁移前后固定路由、直接 URL、Workspace/Space 授权和现有 409 语义不得放宽。
- 迁移必须幂等，可识别已迁移版本；失败时继续读取旧设置并显示迁移失败，而不是静默丢失自定义配置。

### 5. 持久化分为偏好、定义和对象引用

Workbench v1 不使用一个无界 JSON 同时承担所有职责：

1. **Workbench preference**：当前工作台、隐藏/顺序、密度、最近布局和默认入口。适合版本化用户设置，但必须有严格 Schema 和大小上限。
2. **Custom workbench definition**：自定义名称、模块、视图、字段定义和默认范围。需要独立、版本化的服务端实体与 API，以支持查询、迁移、冲突和未来审计。
3. **Workbench object link**：工作台对正式对象的引用、排序、主要上下文和工作台局部属性。必须是独立实体，不得把 `workbench_id` 无审查地添加到每个正式对象。

首个实现切片可以只交付偏好和只读模板投影；自定义定义、对象引用和有限属性必须在各自迁移/OpenAPI/权限门通过后启用。

### 6. 正式对象保持唯一事实源

- Source、Topic、Note 可被多个工作台引用；Excerpt 仍归属 Source；ReviewSchedule 仍归属用户与 Topic。
- Task 和 Claim 有一个主要领域上下文，其他工作台只建立引用。
- 自定义属性默认附着于 Workbench object link，只表达当前工作台的阶段、评分或展示信息，不覆盖正式对象字段。
- 命令必须区分“从当前工作台移除”“添加到其他工作台”“移动主要归属”和“删除正式对象”。
- 删除正式对象必须展示所有可见引用的影响范围；无权查看的引用不得泄露对象或工作台存在性。

首批可引用目标必须使用明确 allowlist 和可验证范围。不得采用无约束 `target_type + target_id` 作为最终数据库完整性方案；准确 typed FK、目标注册表或受控联合模型需要在迁移设计中单独比较。

### 7. Today 统一，Workbench 承载领域差异

- Today 始终回答“现在做什么、为什么、需要什么证据、如何验收”，不建设四套首页。
- Today 项目显示来源工作台，但切换工作台不改变任务、会话、证据或验收的正式状态。
- Workbench 承载领域深度布局：学习项目桌面、研究证据实验台、考试覆盖指挥台、导师审阅台。
- Knowledge Base 和图谱继续使用一个引擎；工作台只改变默认节点类型、过滤、布局和建议动作。

### 8. 视觉差异只出现在工作表面

- 五区 Shell、Context Bar、Inspector、主题、组件、反馈、权限和响应式基线统一。
- 工作台可以改变布局模板、对象行、信息密度、数据可视化和局部视觉签名。
- 工作台辅助色不能表达成功、风险、权限、可信度或正式/候选状态；这些语义继续使用全局状态合同和文字标签。
- 研究的科技感来自关系图、证据路径、实验轨迹和版本信息，不使用霓虹、装饰粒子、无限漂浮或虚假实时指标。

## 迁移与发布边界

1. 先以只读适配器把现有 Persona 投影为 Workbench，不改变服务端授权和旧设置写入。
2. 再增加版本化偏好 Schema 和幂等迁移；双读期只能有一个权威写路径。
3. 自定义定义、对象引用和有限属性分别经过迁移、OpenAPI、威胁模型、配额和 409 门。
4. 固定模板与自定义能力使用独立 Feature Flag；关闭时保留旧 Persona 路径和数据导出。
5. 未经产品 Owner 批准的完整原型，不开始正式 Web 施工；未经迁移/API 审批，不创建生产表或打开写入。

## 验收要求

- 切换工作台不改变 Workspace、Space、Role、权限请求或正式对象数量；
- 四个固定工作台在对象、主行动、队列和可视化上明显不同，不只是换色或卡片顺序；
- Today 始终保持一个统一行动闭环；
- 同一对象跨工作台引用不复制正式数据；
- 自定义配置拒绝未知版本、重复 ID、越权 Space/对象、危险键和超限内容；
- 409 不静默覆盖，多设备冲突提供比较、保留双方或显式选择；
- 固定模板不可删除，自定义删除只删除配置/引用，不删除正式对象；
- Light/Dark、320/390/1024/1440、键盘、axe 和 reduced-motion 全部通过。

## 开放决策

- Workbench preference 是否继续使用 UserSetting，及其精确键名、Schema 和大小上限；
- Custom workbench definition、object link 和有限属性的 DDL、typed target 方案、配额与 API；
- Task/Claim 主要上下文在现有领域模型中的迁移方式；
- 自定义工作台未来是否允许共享配置；首版默认仅个人所有，不产生新的共享权限边界；
- 模板升级、导出/导入和冲突合并的精确协议。

## 后果

- 产品从“路由画像”演进为成熟工作台，同时保持一套权限、对象和应用外壳；
- 自定义能力具有可理解边界，不演变为任意低代码平台；
- 需要新增版本化合同和后续迁移/API 工作，但避免把长期业务状态继续堆入 Persona JSON；
- 本 ADR 只有在产品规格、隔离原型和持久化设计均获批准后才能转为 Accepted；产品 Owner 已单独授权本次脱敏文档基线提交，但这不授权正式实现、部署或生产开关。
