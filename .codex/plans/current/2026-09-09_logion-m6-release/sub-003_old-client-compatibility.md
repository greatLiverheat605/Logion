# M6 删除响应跨版本兼容门

- 父计划：[M6 发布计划](../2026-09-09_logion-m6-release.md)，步骤 2。
- 状态：所有者于 2026-09-09“采取推荐方案”，D-18 已批准并实现；目标验证通过，完整 CI 与新提交远端门禁收口中。
- 依据：[ADR-0031](../../../../docs/adr/0031-entity-deletion.md) 已批准真实删除冲突需持久化、保留本地内容并人工解决；不能为兼容旧客户端静默丢弃 tombstone 或伪装普通内容冲突。
- 边界：本子计划不改变级联/引用阻止删除规则、数据库模型或生产开关。

## 事实

旧 main 的严格校验器拒绝 T-05 新增的三个可选响应字段。普通内容冲突会因
`remote_deleted_at: null` 被拒绝；字段级省略空值已使该用例恢复通过，真正的非空
删除时间仍必须保留。现有 Release offline 测试使用当前代码，尚非旧客户端实证。

## 可审阅方案

推荐补充明确的客户端能力协商：新版客户端声明支持删除响应，服务端仅向该客户端
返回新增摘要与删除时间；旧客户端的普通同步保留既有响应结构。旧客户端遇到自己
不能表达的删除冲突时，返回明确的升级要求并保留未同步内容；不得把删除时间省略后
当作活跃记录，也不得用失败 ACK 消费尚未解决的操作。更新后的客户端须能继续处理
原操作，不能要求清空 IndexedDB 或 Vault。

可复用现有 `sync_control/upgrade_required` 响应；旧 main 校验器实际接受该结构，
offline 客户端已有升级状态处理。实施时须覆盖 Push 与 Pull：不能只移除 Push 的
额外字段而让旧设备在 Pull 删除时误处理待同步内容。升级后的恢复须保留原 cursor、
Outbox 与 Vault，并验证升级状态能安全解除。当前仅完成静态路径核实与旧校验器
验证，尚未声称真实旧客户端运行或恢复通过。

另一方案是将本次发布限定为所有设备统一升级，禁止新旧客户端混用。该方案仍需
可验证的旧版本准入阻止和本地待同步数据保留机制；仅要求用户刷新页面不足以验收。
它会改变上线期间的可用性与设备操作要求，应由所有者明确接受。

## 获准后的实施与验收

1. 固定能力标识及缺省/未知值行为；同步服务端、Web 请求、生成合同和受控跨域头配置，
   如无需某一层变更则记录原因；不引入新的业务权限。
2. 使用旧 main 的真实校验器及客户端代码验证普通 applied/duplicate/rejected/content
   响应；验证新客户端的 impact/details、双向 delete_update、引用拒绝和重放。
3. 复验旧设备未发 Note/Yjs 更新遇到远端删除、重启后内容保留、升级后重新同步与人工
   解决；拒绝自动复活、Outbox 丢失或静默覆盖。旧服务器与新客户端亦需覆盖。
4. 固定新候选，重跑相关 API/offline/Web 测试、完整 CI、合同生成与跨版本检查，
   更新 PR 的真实验证后再进入合并门。

## 决策停止线

不从“开始 M6”推导允许旧客户端丧失同步能力或更改已批准的持久化删除冲突语义。
先完成已授权的依赖与普通冲突修复及检查；所有者确定跨版本策略后继续本子计划。

## 实现与验收证据

- 客户端使用可选的 `X-Logion-Sync-Capabilities: entity-deletion-v1`，缺省、空值、
  未知或相似 token 不授予能力；支持逗号分隔列表，头长度上限 256，CORS 同步更新。
- 旧 Push 的删除请求以及包含扩展删除结果的整批事务返回既有 upgrade 控制，
  无 ACK、无部分写入；旧 Pull 仅对有权读取的删除返回控制，不发送新游标。
- 旧设备已有 epoch 的快照重建需升级，阻止旧页面自动 bootstrap 覆盖 Vault；
  首次初始化和后续分块仍允许。六个 Web 入口与 SyncClient 共用恢复条件，
  新端只有有效 Push/Pull 成功落地后恢复 ready，原设备、epoch 和游标校验保持。
- OpenAPI 仅增加能力头和既有 wire 控制的响应类型；本次 sync-v1 schema、
  生成 wire 类型/校验器、offline schema 与数据库迁移不变。

`pnpm test:sync-compat` 从固定旧 main 提取真实 offline 源码和真实严格校验器，
不复制伪造的旧实现；使用当前锁定的依赖和 fake-indexeddb 运行可复现检查。
